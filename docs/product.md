# TYT (Take Your Time)

## 컨셉

"얼마나 늦장 부려도 되는가"에 답하는 서비스.

기존 앱은 **언제 출발해야 하는가**를 알려준다. TYT는 같은 계산을 반대로 보여준다 — 출발 시각이 아니라 **지금 남은 여유**를 카운트다운한다.

```
여유 = 도착 목표 시각 − 이동 시간 − 준비 시간 − 지금
```

여유가 양수인 동안은 마음 놓고 뭉개도 되고, 0에 가까워지면 나가야 한다. 주는 감정은 "빨리 나가야 해"가 아니라 **"아직 23분은 늦장 부려도 된다"는 허락**이다. 그래서 화면의 주인공은 시각이 아니라 줄어드는 숫자 하나다.

출발점은 만든 사람이 "지금 언제 출발해야 하지?"가 궁금했던 것이다. 그래서 TYT는 **묻는 순간 답하는 도구**지, 알림으로 먼저 말을 거는 도구가 아니다. 이 문장이 아래 설계 결정 대부분의 근거다.

## MVP 범위

| 항목 | 결정 |
| --- | --- |
| 대상 일정 | **단발**. 반복 규칙 없음 |
| 재사용 | 과거 일정 **기록**에서 복제해 새 일정을 만든다 |
| 사용자 | 개인 도구. 여유를 남과 공유하지 않는다 |
| 이동 시간 | 실시간 길찾기 API |
| 이동 수단 | 대중교통 + 자동차. 일정마다 선택 |
| 준비 시간 | 단일 값(분). 단계별 체크리스트는 제외 |
| 상호작용 | **조회(pull)**. 푸시 알림은 MVP 제외 |
| 클라이언트 | 모바일 앱 |

MVP 기능
1. 인증
2. 장소 검색 (출발지·도착지 입력 수단)
3. 일정 생성 — 새로 만들거나 기록에서 복제
4. 기록 조회 (자주 쓴 순)
5. 여유 조회

## 왜 반복이 아니라 단발인가

**반복 일정의 예외 처리가 통째로 사라진다.** 재택, 공휴일, 휴가, "오늘만 10시 출근". 반복 모델에서 제일 지저분한 부분인데, 단발이면 처리할 게 없다. 안 만들면 그만이다.

**외부 API 호출량이 등록자 수가 아니라 실사용에 비례한다.** 반복 모델은 등록된 모든 사용자의 모든 요일 일정을 매일 깨워서 경로 API를 호출해야 한다. 오늘 안 나가는 사람 것까지. 단발이면 사용자가 실제로 조회한 건만 계산한다.

**매일 반복되는 출근은 기록으로 충분하다.** 아침에 기록에서 "회사" 한 번 고르면 출발지·도착지·도착 시각·준비 시간·이동 수단이 다 채워진다. 반복 등록이 주는 이득이 크지 않다.

나중에 반복이 필요해지면 기록 항목에 "월~금 자동 생성" 토글로 붙일 수 있다. 여유 계산은 그 일정이 반복인지 1회인지 **모르기 때문**에, 변이점은 "다음 도착 목표 일시를 어떻게 뽑는가" 한 곳이다.

## 왜 알림이 MVP가 아닌가

이 서비스는 사용자가 궁금해서 앱을 열 때 답하면 된다. **앱을 여는 행위 자체가 질문**이라 "열어야 한다는 걸 까먹는" 문제가 성립하지 않는다.

그리고 알림을 빼면 MVP에서 제일 무거운 부분이 그대로 빠진다 — 푸시 인프라(FCM·디바이스 토큰)와 **주기 재계산 스케줄러**. 스케줄러가 필요했던 이유는 "교통 상황에 따라 알림 쏠 시각이 움직인다"였는데, 조회가 핵심이면 **조회하는 순간 계산하면 그만**이다.

나중에 붙일 때도 무겁지 않다. 재계산 대상이 "등록된 모든 일정"이 아니라 **"조회하고 알림을 켠 일정"**뿐이라 양이 비교가 안 된다.

## 여유 계산

```
departBy = 도착 목표 시각 − 이동 시간
여유     = departBy − 준비 시간 − 지금
```

### 순환 의존을 인지할 것

이동 시간은 **언제 출발하는지**에 따라 달라지고(교통량), 출발 시각은 이동 시간으로 정해진다. 즉 정의가 스스로를 참조한다.

```
departBy = 도착목표 − travelTime(출발시각 = departBy)
```

MVP 해법: 1회 근사로 끊는다.
1. 도착 목표 시각을 출발 시각으로 넣어 이동 시간을 조회한다
2. 나온 `departBy`를 출발 시각으로 다시 조회해 이동 시간을 갱신한다
3. 거기서 멈춘다. 더 반복해도 분 단위에서 의미 있게 수렴하지 않는다

여유가 크면 `departBy`가 몇 시간 뒤라, "지금 출발" 기준 경로 API만으로는 부족하다. 출발 시각을 지정할 수 있는 API(TMAP 타임머신 계열)가 필요하다.

## 기록

과거에 만든 일정 목록이 곧 기록이다. **별도의 프리셋/템플릿 엔티티를 두지 않는다.** 프리셋을 따로 두면 관리 화면이 하나 더 생기고, 프리셋을 고쳤을 때 진행 중인 일정이 흔들리는 문제까지 떠안는다.

새 일정은 기록에서 복제해 만든다. 값은 생성 시점에 복사되므로 과거 일정을 나중에 고쳐도 이미 만든 일정은 흔들리지 않는다.

같은 곳을 매일 만들면 기록이 똑같은 항목으로 도배되는데, 이건 **읽기 쪽에서** 푼다. 조회할 때 (출발지, 도착지, 도착 시각)으로 묶어 자주 쓴 순으로 보여준다. 쓰기 모델은 단순하게 둔다.

## 도메인 분할

```
user      인증, 사용자
schedule  Schedule(aggregate), 기록 조회, 여유 계산
```

- 패키지 이름은 `commute`가 아니라 `schedule`. 출근도 약속도 "도착 목표가 있는 일정"이라는 같은 개념이다.
- 여유 계산은 `schedule` 안에 둔다. 계산 입력이 전부 `Schedule`에 있어서, 밖으로 빼면 도메인 간 참조만 늘어난다.
- 이동 시간 조회와 장소 검색은 도메인이 아니다. `schedule/application/port/out`의 Port ← `schedule/infrastructure/client`의 adapter.
- 알림을 도입하면 `notification` 도메인이 생긴다. 그때 여유 소진 알림은 **이벤트가 아니라 UseCase 직접 호출**로 한다. AFTER_COMMIT 이벤트는 수신 실패 시 유실되는데, 이 알림이 유실되면 기능이 존재할 이유가 없어진다.

## 외부 의존

| 용도 | 후보 | 메모 |
| --- | --- | --- |
| 자동차 경로·소요시간 | TMAP (자동차 길안내 / 타임머신) | 실시간·예측 교통정보 반영. 응답에 `totalTime` |
| 대중교통 경로·소요시간 | TMAP 대중교통 API, ODsay | TMAP은 `totalTime` + 구간별 `sectionTime`. ODsay는 Basic(개인·5인 이하 스타트업) 무료 구간 있음 |
| 장소 검색 | 경로 API와 같은 벤더 | 좌표를 직접 입력할 수는 없으므로 POI 검색이 필요하다 |
| 푸시 | FCM | 알림 도입 시 |

대중교통·자동차·장소 검색을 **한 벤더(TMAP)로 묶을 수 있는지**를 먼저 검증한다. 묶이면 키 발급과 계약이 한 번으로 끝난다.

## 미결정 사항

- 경로 API 무료 호출 한도. 조회할 때만 호출하므로 반복 모델보다 훨씬 적지만, 한도를 알아야 캐시 정책을 정할 수 있다.
- 같은 일정을 연속으로 새로고침할 때의 캐시 TTL. 교통 상황이 분 단위로 바뀌지는 않는다.
- 기록의 그룹핑·정렬 기준 (자주 쓴 순 / 최근 순 / 둘 다).
- 도착 목표 시각을 매번 입력받을지, 기록에 담긴 시각을 기본값으로 채울지.
- 위치 기반으로 집에 있는지 판단하는 건 MVP 제외.
