# TYT (Take Your Time)

## 컨셉

"얼마나 늦장 부려도 되는가"에 답하는 서비스.

기존 앱은 **언제 출발해야 하는가**를 알려준다. TYT는 같은 계산을 반대로 보여준다 — 출발 시각이 아니라 **지금 남은 여유**를 카운트다운한다.

```
여유 = 도착 목표 시각 − 이동 시간 − 준비 시간 − 지금
```

여유가 양수인 동안은 마음 놓고 뭉개도 되고, 0이 되는 순간 알림이 온다. 주는 감정은 "빨리 나가야 해"가 아니라 **"아직 23분은 늦장 부려도 된다"는 허락**이다. 그래서 화면의 주인공은 시각이 아니라 줄어드는 숫자 하나다.

## MVP 범위

| 항목 | 결정 |
| --- | --- |
| 대상 일정 | **출근만**. 요일 반복 일정. 단발 약속은 MVP 제외 |
| 사용자 | 개인 도구. 여유를 남과 공유하지 않는다 |
| 이동 시간 | 실시간 길찾기 API |
| 이동 수단 | 대중교통 + 자동차. 일정마다 선택 |
| 준비 시간 | 단일 값(분). 단계별 체크리스트는 제외 |
| 클라이언트 | 모바일 앱. 알림은 FCM 푸시 |
| 알림 갱신 | 서버가 주기적으로 재계산해 알림 시각을 갱신 |

MVP 기능
1. 인증
2. 출근 일정 CRUD (출발지, 도착지, 도착 목표 시각, 반복 요일, 준비 시간, 이동 수단)
3. 여유 조회
4. 여유 소진 푸시 알림
5. 디바이스 토큰 등록

## 여유 계산

```
departBy = 도착 목표 시각 − 이동 시간
여유     = departBy − 준비 시간 − 지금
```

### 순환 의존을 인지할 것

이동 시간은 **언제 출발하는지**에 따라 달라지고(교통량), 출발 시각은 이동 시간으로 정해진다. 즉 정의가 스스로를 참조한다.

```
departBy = 도착목표 − travelTime(출발시각 = departBy)
```

MVP 해법: 1회 근사로 끊는다.
1. 도착 목표 시각을 출발 시각으로 넣어 이동 시간을 조회한다
2. 나온 `departBy`를 출발 시각으로 다시 조회해 이동 시간을 갱신한다
3. 거기서 멈춘다. 더 반복해도 분 단위에서 의미 있게 수렴하지 않는다

미래 출발 시각 기준 예측이 필요하므로 "지금 출발" 기준 경로 API만으로는 부족하다. TMAP 타임머신 API처럼 출발 시각을 지정할 수 있는 API가 필요하다.

## 반복 일정과 단발 약속

출근(반복)만 만들어도 단발 약속은 나중에 값싸게 붙는다. 여유 계산은 `도착 목표 일시`, `이동 시간`, `준비 시간`, `now` 네 입력만 쓰고, 그 일정이 반복인지 1회인지 **모른다**. 차이는 "다음 도착 목표 일시를 어떻게 뽑는가" 한 지점뿐이다.

```
반복: (월~금, 09:00) + now  →  다음 도착 일시  ┐
단발: (2026-09-20 15:00)    →  다음 도착 일시  ┴→ 여유 계산 (공통)
```

그래서:
- 요일·시각을 엔티티 필드로 날것으로 두지 말고 `RecurrenceRule` VO로 감싼다. 지금은 `WEEKLY`만 구현한다. 나중에 단발을 추가할 때 DB 마이그레이션과 API 변경이 이 VO 안에 갇힌다.
- `ONCE` 타입은 지금 구현하지 않는다.

순서가 이 방향인 게 이득이다. 반복 일정에는 단발에 없는 문제(재택·공휴일·휴가·"오늘만 10시")가 딸려오고, 그 예외는 결국 "특정 날짜 1회 오버라이드" — 단발과 같은 구조다. 어려운 쪽을 먼저 푸는 셈.

## 도메인 분할

```
user          인증, 사용자
schedule      CommuteSchedule(aggregate), RecurrenceRule, 여유 계산
notification  푸시 발송, 디바이스 토큰
```

- 패키지 이름은 `commute`가 아니라 `schedule`. 출근도 약속도 "도착 목표가 있는 일정"이라는 같은 개념이고, 단발을 붙일 때 경계 이름을 바꾸지 않아도 된다.
- 여유 계산은 `schedule` 안에 둔다. 계산 입력이 전부 `CommuteSchedule`에 있어서, 밖으로 빼면 도메인 간 참조만 늘어난다.
- 이동 시간 조회는 도메인이 아니다. `schedule/application/port/out/TravelTimePort` ← `schedule/infrastructure/client`의 TMAP adapter.
- 주기 재계산도 도메인이 아니다. `schedule/infrastructure/scheduler`.
- 여유 소진 알림은 **이벤트가 아니라 UseCase 직접 호출**로 한다. `schedule.infrastructure.client.NotificationAdapter` → `notification.application.port.in.SendPushUseCase`. AFTER_COMMIT 이벤트는 수신 실패 시 유실되는데, 이 알림이 유실되면 서비스가 존재할 이유가 없어진다.

## 외부 의존

| 용도 | 후보 | 메모 |
| --- | --- | --- |
| 자동차 경로·소요시간 | TMAP (자동차 길안내 / 타임머신) | 실시간·예측 교통정보 반영. 응답에 `totalTime` |
| 대중교통 경로·소요시간 | TMAP 대중교통 API, ODsay | TMAP은 `totalTime` + 구간별 `sectionTime`. ODsay는 Basic(개인·5인 이하 스타트업) 무료 구간 있음 |
| 푸시 | FCM | |

대중교통과 자동차를 **한 벤더(TMAP)로 묶을 수 있는지**를 먼저 검증한다. 묶이면 키 발급과 계약이 한 번으로 끝난다.

## 미결정 사항

- **API 호출량**: 사용자 수 × 하루 재계산 횟수. 출근은 아침 한두 시간에 전부 몰려서 피크가 평균보다 훨씬 크다. 재계산 간격·캐싱 정책과 무료 한도를 확인해야 MVP 비용이 나온다.
- 재계산 구간: 도착 목표 몇 시간 전부터, 몇 분 간격으로 돌릴지.
- "오늘은 출근 안 함"(재택·휴가·공휴일) 처리 범위.
- 위치 기반으로 집에 있는지 판단하는 건 MVP 제외.
